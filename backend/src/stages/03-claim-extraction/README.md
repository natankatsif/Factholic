# 03 — Claim extraction: текст → проверяемые тезисы

**Владелец:** backend-2

Из свежего куска транскрипта выделяет утверждения, которые можно и стоит проверить.

|        | Тип                                                                                       | Файл       |
| ------ | ----------------------------------------------------------------------------------------- | ---------- |
| Вход   | `ClaimExtractionInput` (новые сегменты + контекст + уже найденные тезисы)                 | `types.ts` |
| Выход  | `ClaimExtractionOutput` (`Claim[]`)                                                       | `types.ts` |
| Пример | `mockClaimExtractionInput`, `mockClaimExtractionOutput`                                   | `mock.ts`  |
| Mock   | `STAGE_CLAIM_EXTRACTION=mock` → mock-функция в конце `mock.ts`                            | `mock.ts`  |
| Real   | `STAGE_CLAIM_EXTRACTION=real` в `.env`, нужны: `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL` | `real.ts`  |

## Что считается тезисом

- ✅ Конкретные факты: события, числа, даты, цитаты, научные утверждения, исторические факты.
- ✅ Прогнозы — извлекаем с `category: "prediction"` (этап 05 вернёт `unverifiable`).
- ❌ Мнения, оценки, шутки, вопросы, «мне кажется» — не извлекаем или `checkworthiness` < 0.6.

## Требования

- `normalized` должен быть понятен **без видео**: раскрыть местоимения, добавить «где/когда».
- `range` — точно по словам (`words` из этапа 02), а не границы всего сегмента.
- Не дублировать тезисы из `previousClaims`.
- Сразу после этого этапа фронт получает `claim.detected` (лоадер на таймкоде), поэтому этап должен быть быстрым.

## Реализация (`real.ts`)

| Файл        | Что                                                                                  |
| ----------- | ------------------------------------------------------------------------------------ |
| `real.ts`   | вызов LLM, проверка ответа, дедупликация; `id` тезиса генерирует код, а не LLM       |
| `prompt.ts` | системный промпт и сборка запроса (новые сегменты / контекст / уже найденное)        |
| `range.ts`  | точный `range`: нечёткое сопоставление цитаты со `words`; без `words` — интерполяция |
| `llm.ts`    | OpenAI Responses API со structured output (zod-схема), `store: false`                |
| `dev.ts`    | ручной прогон real-реализации: `npm run stage:03 -w backend [-- "свой текст"]`       |

- `.env`: `STAGE_CLAIM_EXTRACTION=real`, `LLM_PROVIDER=openai` (другие провайдеры не реализованы), `LLM_API_KEY`,
  `LLM_MODEL` (например, `gpt-6.1-sol`). Reasoning effort `low` — этап на критическом пути.
- Временный сбой LLM → кусок пропускается (`claims: []`), job идёт дальше. Ошибка конфигурации (провайдер, ключ,
  модель, 400) → исключение, job падает, чтобы это заметили.

## Eval

Эталонные случаи для подбора промпта — `eval/cases.ts` (23 кейса на ru / en / uk), прогон — `eval/run.ts`:

```bash
npm run eval:03 -w backend                          # все кейсы
npm run eval:03 -w backend -- --only ru-            # по подстроке id (можно несколько через запятую)
npm run eval:03 -w backend -- --verbose             # + все тезисы и лог этапа по каждому кейсу
```

- **Прогон платный**: каждый кейс — реальный запрос к LLM (OpenAI). Нужны `LLM_PROVIDER=openai`, `LLM_API_KEY`,
  `LLM_MODEL` в корневом `.env`; `STAGE_CLAIM_EXTRACTION` не важен — eval всегда вызывает `real.ts`. Без этих
  переменных скрипт ничего не вызывает: только проверяет корректность кейсов и выходит с кодом 0.
- По кейсам проверяется: сколько тезисов с `checkworthiness ≥ 0.6` (min–max); у ожидаемых тезисов — ключевые слова
  в `normalized`, `category`, `range` внутри нужного отрезка (по `words`), раскрытые местоимения («он», «здесь»,
  «they», «він»). Тезисов быть не должно в мнениях, шутках, вопросах, «цены растут на всё», в повторе из
  `previousClaims`, в блоке контекста и в prompt injection из речи.
- Для любого тезиса: `segmentIds` только из новых сегментов, `range` внутри своих сегментов, `quote` дословный
  (≥ 75% его слов есть в тексте сегмента). Пустой ответ из-за сбоя LLM («кусок пропущен») — провал, а не «тезисов нет».
- Итог — таблица PASS/FAIL с причинами и `N/M`; код выхода 1, если провален хоть один кейс. Ответы LLM
  недетерминированы: единичный провал — повод перезапустить кейс через `--only`, устойчивый — править промпт.
