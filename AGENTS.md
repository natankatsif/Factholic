# AGENTS.md — контекст проекта для любого AI-агента и нового разработчика

> Прочитай этот файл целиком перед любой задачей. Во вложенных папках (`backend/`, `extension/`,
> `packages/contracts/`) лежат свои `AGENTS.md` с правилами конкретной зоны, а в каждой папке этапа — `README.md`.

> ⛔ **Агенты не коммитят и не пушат.** Коммиты делает только человек. Агент может лишь _предложить_ коммит —
> см. раздел [«Git: коммитит только человек»](#git-коммитит-только-человек).

## 1. Что мы строим

**FactCheck Video** — расширение для Chrome (Manifest V3), которое проверяет факты в видео **прямо во время просмотра**.

Пользователь открывает любое видео (YouTube, новостной сайт, что угодно с `<video>`). Расширение:

1. находит видео на странице;
2. бэкенд расшифровывает речь в текст с таймкодами;
3. выделяет из текста **проверяемые утверждения** (тезисы);
4. для каждого тезиса ищет **несколько источников с разных точек зрения**;
5. выставляет **оценку достоверности 0–10** с коротким объяснением;
6. расширение показывает её **поверх плеера ровно в тот момент**, когда тезис произносится.

Пример: на 20:21–20:23 спикер говорит «в Украине сейчас идёт война» → в эти секунды поверх видео появляется карточка
«10/10 · Правда · Подтверждается международными организациями и СМИ разных стран» + 4 источника со ссылками.

### Пользовательский сценарий

```
открыл страницу с видео
  → расширение нашло <video>, отправило POST /api/jobs (со своей текущей позиции)
  → на таймлайне/в углу индикатор «анализ идёт», прогресс processedUntil
  → бэк нашёл тезис           → на его таймкоде появляется «Проверяем…»       (claim.detected)
  → бэк проверил тезис         → лоадер заменяется оценкой, вердиктом, источниками (claim.checked)
  → пользователь досмотрел до таймкода → карточка всплывает поверх видео, клик → подробности и источники
  → перемотал                  → бэк переключается на новый участок (ClientMessage "playback")
```

Цель по скорости: для видео, которые бэкенд может скачать сам (режим `remote`), обрабатывать **с опережением**,
чтобы оценка была готова к моменту, когда пользователь дойдёт до тезиса.

## 2. Принципы продукта (не нарушать)

1. **Оценка только по найденным источникам.** Модель не должна выставлять оценку «из головы»: нет источников —
   `unverifiable`, а не догадка. Пользователь должен иметь возможность проверить нас по ссылкам.
2. **Разные точки зрения.** Источники разных типов (международные организации, госорганы, СМИ, наука,
   фактчекеры), стран и языков. Не 5 статей одного издания.
3. **Нейтральный тон.** `summary`/`explanation` — без оценочных эпитетов, без политической позиции.
   Если источники противоречат друг другу — `mixed`, и так и пишем.
4. **Проверяем факты, а не мнения.** Мнения, шутки, вопросы, оценочные суждения не извлекаются. Прогнозы
   извлекаются, но получают `unverifiable`.
5. **Прозрачность.** Всегда показываем дословную цитату (`quote`), переформулированный тезис (`claim`),
   и позицию каждого источника (`stance`).
6. **Не мешать просмотру.** Оверлей ненавязчивый, не перекрывает субтитры и элементы управления плеера.

## 3. Архитектура

```
 [extension]                                [backend]
 нашёл <video> ──POST /api/jobs──▶  01 ingest           видео → куски звука/субтитров по ~30 с
                                         │ MediaChunk
                                    02 transcription    → текст с абсолютными таймкодами
                                         │ TranscriptionOutput (TranscriptSegment[])
                                    03 claim-extraction → тезисы ─────────────┐
                                         │ Claim                              │ WS: claim.detected (лоадер)
                                    04 source-search    → источники           │
                                         │ FoundSource[]                      │
                                    05 verification     → оценка 0–10         │
                                         │ VerificationOutput                 │
 оверлей на таймкоде ◀──WS───────── 06 delivery         → FactCheck ◀─────────┘ WS: claim.checked
```

- Куски видео обрабатываются **по порядку**, тезисы внутри куска — **параллельно** (`backend/src/pipeline/orchestrator.ts`).
- Каждый этап — функция `Stage<Input, Output> = (input, ctx: StageContext) => Promise<Output>`
  (`backend/src/pipeline/context.ts`). Этапы **не импортируют реализации друг друга** — только типы (`types.ts`).
  Связывает их только оркестратор.
- Протокол: `POST /api/jobs` → `{ jobId, eventsUrl }` → WebSocket. Сервер шлёт `ServerEvent`, клиент шлёт
  `ClientMessage` (позиция плеера, звук в live-режиме, отмена). Всё в `packages/contracts/src/api.ts`.

### Этапы

| #   | Папка `backend/src/stages/` | Вход → Выход                                     | Владелец  | Суть                                                        |
| --- | --------------------------- | ------------------------------------------------ | --------- | ----------------------------------------------------------- |
| 01  | `01-ingest`                 | `IngestInput` → `IngestOutput`                   | backend-1 | скачать видео/субтитры (`remote`) или принять звук (`live`) |
| 02  | `02-transcription`          | `TranscriptionInput` → `TranscriptionOutput`     | backend-1 | ASR с пословными таймкодами; субтитры — без ASR             |
| 03  | `03-claim-extraction`       | `ClaimExtractionInput` → `ClaimExtractionOutput` | backend-2 | LLM выделяет проверяемые тезисы, точный `range` по словам   |
| 04  | `04-source-search`          | `SourceSearchInput` → `SourceSearchOutput`       | backend-2 | запросы на разных языках, поиск, вырезка релевантных кусков |
| 05  | `05-verification`           | `VerificationInput` → `VerificationOutput`       | backend-2 | LLM сопоставляет тезис с источниками → score, label, тексты |
| 06  | `06-delivery`               | `DeliveryInput` → `FactCheck` (из contracts)     | backend-1 | чистый маппер во фронтовую модель (уже реализован)          |

### Режимы получения звука

- `remote` — бэкенд сам качает по `pageUrl` (yt-dlp). Если есть субтитры платформы — берём их, ASR не нужен.
  Можно обрабатывать наперёд.
- `live` — видео нельзя скачать (`blob:`, DRM, закрытые сайты). Расширение захватывает звук вкладки
  (`chrome.tabCapture` + offscreen document) и шлёт `audio.chunk` по WS. Оценки приходят с задержкой.

## 5. Контракты — два уровня

| Уровень       | Где                                | Кто использует               | Как менять                                 |
| ------------- | ---------------------------------- | ---------------------------- | ------------------------------------------ |
| Сетевой       | `packages/contracts/src/*`         | бэкенд **и** расширение      | только по договорённости всех троих        |
| Между этапами | `backend/src/stages/NN-*/types.ts` | следующий этап + оркестратор | договориться с владельцем следующего этапа |

Правила:

- **Типы — источник правды.** Сначала меняешь тип, потом код. Не дублируй типы в других местах — импортируй.
- Меняешь тип → **обнови `mock.ts`** того же этапа (и мок в contracts, если менял `FactCheck`). Моки — живая
  документация и данные для дизайна; они должны компилироваться.
- Внутренние поля пайплайна (`excerpt`, `domainReliability`, `checkworthiness`, `model`…) **не попадают** в
  `packages/contracts`. Фронт знает только `FactCheck` и протокол.
- Все времена — **абсолютные секунды от начала видео** (`Seconds`, дробные). Строка «20:21–20:23» — только
  через `formatRange()` на фронте.
- Шкала оценки: `score` 0–10 целое, `null` только при `label: "unverifiable"`. Соответствие score ↔ label —
  в `backend/src/stages/05-verification/README.md`.

## 6. Юниты и владельцы

Проект делят три человека. Код разбит на **юниты** (`scripts/units.mjs`), у каждого — владелец:

| Юнит                              | Владелец  |
| --------------------------------- | --------- |
| `contracts`                       | все трое  |
| `backend-01-ingest`               | backend-1 |
| `backend-02-transcription`        | backend-1 |
| `backend-03-claim-extraction`     | backend-2 |
| `backend-04-source-search`        | backend-2 |
| `backend-05-verification`         | backend-2 |
| `backend-06-delivery`             | backend-1 |
| `backend-core` (server, pipeline) | backend-1 |
| `extension`                       | frontend  |

**Агент работает внутри одного юнита**, если задача явно не требует иного. Нужна правка в чужом юните или в
контракте — сделай минимальную правку и **явно напиши об этом в итоговом отчёте** («изменил `Claim` в
`03/types.ts`: добавил поле X, затронуты 04 и оркестратор»).

## 7. Как агенту выполнять задачу

1. Определи юнит. Прочитай его `README.md`, `types.ts`, `mock.ts` и `AGENTS.md` зоны.
2. Входные данные этапа смотри в `mock.ts` **предыдущего** этапа, выход должен совпадать по форме с `mock.ts` своего.
3. Реализуй в `index.ts` (можно добавлять файлы в папку этапа). Сигнатуру экспортируемой функции не менять.
4. Не трогай `types.ts`, если задача этого не требует. Если требует — см. раздел 5.
5. Запусти `npm run check -- <юнит>`; для бэкенда end-to-end — `npm run dev` и подключись к WS.
6. Секреты (API-ключи ASR/LLM/поиска) — только через `process.env`, в `.env` (он в `.gitignore`). Никогда в код.
7. В отчёте: что сделано, какие юниты/контракты затронуты, что осталось TODO.
8. Если работа логически закончена и `npm run check` зелёный — **предложи коммит** (см. следующий раздел).

## Git: коммитит только человек

Агент (Claude Code, Codex, Cursor, любой другой) **никогда не выполняет** `git commit`, `git push`, `git add`,
`git merge`, `git rebase`, `git reset`, `git stash`, не создаёт и не удаляет ветки и теги — даже если пользователь
попросил «сделай всё». Исключение — только явная фраза пользователя вида «закоммить сам» в текущем сообщении.
Чтение можно: `git status`, `git diff`, `git log`, `git show`, `git blame`.

Когда работа дошла до логической точки (фича/фикс готов, `npm run check` зелёный), агент в конце ответа
**предлагает** коммит — одним блоком, который человек может скопировать:

```
💾 Предлагаю закоммитить (юнит: backend-03-claim-extraction):

git add backend/src/stages/03-claim-extraction/
git commit -m "03: извлечение тезисов через LLM со structured output"
```

- В `git add` — только файлы своей задачи, перечисленные явно (не `git add -A` / `git add .`).
- Сообщение — на русском, в начале номер этапа или зона (`03:`, `ext:`, `contracts:`, `core:`).
- Если затронут контракт — сказать об этом рядом с предложением.
- Предлагать не после каждой правки, а когда есть законченный, проверенный кусок.

Как это обеспечено:

- `.claude/settings.json` (общий, в git) — Claude Code запрещены `git commit` и `git push` у всех, кто работает в папке.
- `.husky/pre-commit` — если коммит запущен из оболочки Claude Code (`CLAUDECODE=1`), хук его отклоняет.
  Поэтому и человек коммитит из **обычного терминала или IDE**, а не через `!` внутри Claude Code.
- Для остальных агентов — это правило в `AGENTS.md`.

## 8. Конвенции кода

- TypeScript strict, ESM, Node 22. Импорты — с расширением `.ts` (`import … from "./types.ts"`).
- Импорт типов — только `import type` (включены `verbatimModuleSyntax` и eslint `consistent-type-imports`).
- Модули этапов: `index.ts` делает `export type * from "./types.ts"`; значения (константы) реэкспортируются
  отдельно (`export { X } from "./types.ts"`).
- Комментарии и документация — **на русском**. Идентификаторы — на английском.
- Форматирование — prettier (`printWidth: 110`), не спорим, хук всё отформатирует сам.
- `index.ts` этапа, который ещё не реализован, возвращает данные из `mock.ts` и помечен `TODO(<владелец>)`.
- Внешние вызовы (LLM, ASR, поиск) принимают `ctx.signal` для отмены, когда пользователь ушёл со страницы.
- Тестов пока нет; эталоном формы данных служат `mock.ts`.

## Проверки и pre-commit

`npm install` ставит хук через husky (`.husky/pre-commit` → `lint-staged`). При `git commit`:

1. **eslint --fix** и **prettier --write** — только по застейдженным файлам (`lint-staged.config.mjs`).
2. **tsc** — только по юнитам, которых касаются застейдженные файлы (`scripts/check.mjs --staged`).
   Каждый этап бэкенда имеет свой `tsconfig.json`, поэтому проверяется изолированно.

Что это даёт:

| Ситуация                                                            | Результат                                     |
| ------------------------------------------------------------------- | --------------------------------------------- |
| коммитишь этап 01, а в рабочей копии лежит сломанный этап 03        | ✅ коммит проходит, 03 не проверяется         |
| коммитишь сломанный этап 03                                         | ❌ блок, показан юнит, владелец и ошибки      |
| меняешь `stages/*/types.ts` или `mock.ts` и это ломает другие этапы | ❌ блок: проверяется весь бэкенд              |
| меняешь `packages/contracts/**` и это ломает бэк или расширение     | ❌ блок: проверяются backend-core и extension |
| меняешь корневые конфиги (`tsconfig.base.json`, `package.json`)     | проверяются все юниты                         |

Команды:

```bash
npm run check                  # все юниты, tsc + eslint, отчёт ✅/❌
npm run check -- 03 extension  # выбранные юниты (по подстроке id)
```

Добавил новый модуль (например `extension/src/popup` — он внутри `extension`, ничего делать не надо; новый пакет —
нужно) → добавь юнит в `scripts/units.mjs` и `tsconfig.json` для него.
Обходить хук (`--no-verify`) нельзя, кроме аварийных случаев с явным согласия команды.

## 11. Принятые решения

- **Монорепо на npm workspaces**, типы шарятся через `@news/contracts` (TS-исходники без сборки).
- **WebSocket, а не SSE**: в MV3 service worker нет `EventSource`, а для live-режима нужен канал клиент → сервер.
- **Субтитры платформы приоритетнее ASR**: быстрее, дешевле, точнее.
- **Обработка с `startFrom`**, а не с начала видео: пользователю важно то, что он смотрит сейчас.
- **Два события на тезис** (`claim.detected` → `claim.checked`): UI сразу показывает, что тезис замечен,
  проверка (поиск + LLM) занимает секунды.
- **Сборка расширения — esbuild без UI-фреймворка** на старте; фронт вправе перейти на Vite/React, контракты не меняются.

## 13. Глоссарий

- **Job** — одна сессия анализа одного видео (`jobId`).
- **Кусок (chunk)** — ~30 с видео, единица обработки этапов 01–02.
- **Сегмент** — фраза транскрипта с таймкодами.
- **Тезис (claim)** — проверяемое утверждение из речи; `quote` — дословно, `normalized`/`claim` — самодостаточная формулировка.
- **Источник (source)** — найденная страница; `stance` — подтверждает / опровергает / смешанно / нейтрально.
- **Вердикт (verdict)** — `score` 0–10 + `label` + `summary` + `explanation`.
- **FactCheck** — итоговая сущность для фронта: тезис + вердикт + источники + таймкод.
- **Юнит** — независимо проверяемая часть кода со своим владельцем (`scripts/units.mjs`).
